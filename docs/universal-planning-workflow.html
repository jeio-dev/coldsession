Define → Plan → Review → Revise → Approve → Build

A six-step loop for planning software with an AI coding agent. Every step is gated by task IDs and finding IDs, so nothing moves forward on a vague "looks good." State lives on disk from Step 1 in PLAN.md and a phase file, and every step that judges the previous one runs in a fresh session so it can't inherit the assumptions it's supposed to catch.

SScale

Pick a gear first

The full loop costs four sessions before a line of code exists. That pays for itself on a new surface area and is pure overhead on a copy change. Match the gear to the blast radius, not to the enthusiasm.

Direct
Skip the workflow. Reversible, one or two files, obvious correct answer. Just ask for the change.
Short loop
Plan → Review → Build, one session, no files on disk. A feature inside existing architecture. Skip Define, Revise inline, no formal approval.
Greenfield
Define → Groundwork → full loop. Empty repo. Nothing to read, no conventions to follow, no commands that work. Step G exists to end that state before Step 1 runs.
Full loop
All six steps, split across sessions. New app, new phase, schema changes, auth, payments, anything where being wrong is expensive to unwind.
>

Touching data ownership, auth, or money puts you in the full loop regardless of how small the diff looks.

RRuntime

Route the model to the step

This section describes Claude Code's optional model routing. Codex runs the same workflow with the model, effort, and collaboration mode selected for the active Codex session.

Planning is worth the expensive model. Executing an approved spec is not. Rather than remembering that at 4am, let the alias do it: in opusplan, plan mode runs Opus and execution runs Sonnet.

.claude/settings.json
{
  "model": "opusplan",
  "env": {
    "CLAUDE_CODE_SUBAGENT_MODEL": "sonnet"
  }
}

Which gives one rule for the whole workflow: reason in plan mode, exit plan mode to write. The thinking runs on Opus, the typing runs on Sonnet, and the reasoning is already in context by the time the cheaper model does the writing.

>

Exiting plan mode changes model, and the next response re-reads the full history without cached context. That's fine once per session and expensive if you toggle back and forth. Reason, exit, write, stop.

Build effort
Launch build sessions with claude --effort medium. The ladder is low / medium / high / xhigh / max, the default is high, and a task that already survived a review cycle doesn't need it.
Check the defaults
A model chosen with /model is saved into ~/.claude/settings.json and quietly applies to every session after. effortLevel in the same file behaves the same way. Clear both keys so the project setting and the launch flag win.
Never switch mid-session
Set the model at launch with --model, which is session-only. Switching inside a long conversation re-reads the entire history uncached.

Every step below carries the mode and model it should run on.

CCommands

Commit the prompts, don't paste them

The prompts below are long on purpose, and pasting a 30-line block by hand at every step is where this workflow rots. The text drifts between projects, an improvement you make today is invisible to every repo already mid-phase, and nothing records which version of the loop a given plan was built under.

Commit each step as a command file instead. The page you're reading then holds the reasoning — why a fresh session, why the gear rule — and the repo holds the executable version, which git can diff.

How a command file works

A command is a markdown file in .claude/commands/. The filename becomes the slash name, so cs-build.md gives you /cs-build. The frontmatter is metadata for the picker; the body below it is the prompt, sent verbatim. $ARGUMENTS is replaced by everything you typed after the command name, and $1 by the first word of it. Put the files in .claude/commands/ to commit them with the repo, or ~/.claude/commands/ to have them everywhere.

Codex uses repository-scoped skills instead. The installer adds ten adapters under .agents/skills/; each one loads a runtime-patched copy of the same canonical command from .agents/coldsession/commands/. Invoke /cs-build T2 in Claude Code or $cs-build T2 in Codex. The product-specific sigil differs; the cs-* stem and arguments are the same.

every prompt below is one of these
.claude/commands/
├── cs-define.md      /cs-define <rough idea>   step 0
├── cs-groundwork.md  /cs-groundwork            step G, greenfield only
├── cs-plan.md        /cs-plan                  step 1
├── cs-review.md      /cs-review                step 2, round 1
├── cs-recheck.md     /cs-recheck               step 2, round 2 and after
├── cs-revise.md      /cs-revise                step 3
├── cs-approve.md     /cs-approve               step 4
├── cs-build.md       /cs-build T7              build, one task
├── cs-close.md       /cs-close                 phase close
└── cs-status.md      /cs-status                where am I

.claude/bin/plan   the task graph tool every command above calls

Each step below is printed as its finished command file — frontmatter included, placeholders already replaced with arguments. Copy the block, save it at the path in its header, and that step is a slash command. Nothing else in this document changes.

What a command does not carry

This is the part that bites. A command supplies the prompt text and nothing else. It does not start a new session, it does not enter plan mode, and it does not pick a model. Typing /cs-review in the session that just wrote the plan gives you a compromised review with correct wording, which is worse than no review because it looks like one.

You do
Start the session, enter or exit plan mode, set --effort at launch. The session and mode chips on each step below are still the instruction — the command file can't enforce them.
Settings do
Model routing, via opusplan in .claude/settings.json. Plan mode gets Opus, execution gets Sonnet, with no per-command configuration.
The command does
The prompt text, the argument substitution, and the fact that it's the same text in every repo and every run.

Setting it up

bash
cd ~/my-project
git clone --depth 1 --branch v2.0.0 https://github.com/<you>/coldsession .coldsession
.coldsession/install.sh --agent both
git add .claude .agents templates && git commit -m "chore: coldsession"

The clone goes inside the project and the installer deletes it when it's done, so the only copy of the workflow that outlives the install is the one committed with the code.

Installing per project rather than globally is deliberate: the workflow version is pinned with the code, so a phase planned six months ago still reads the way it was planned. Record it: add workflow-rev: 1.3.0 to PLAN.md's frontmatter, so a phase planned under an older loop is readable as an older plan rather than a wrong-looking one.

Session 1
Plan mode · opus

Turn the idea into an objective

Run this once, before Step 1 has anything to plan. It converts a rough app idea into a scoped brief.

.claude/commands/cs-define.md
---
description: Turn a rough idea into a scoped objective brief
argument-hint: [rough app idea]
---

Help me turn this idea into a well-defined objective I can hand off for
detailed planning:

$ARGUMENTS

If the line above is blank, ask me for the idea and stop.

Produce an Objective Brief containing:
- Problem statement: what problem this solves, and for whom
- Core value proposition, in one or two sentences
- Primary users and their main use case
- MVP feature list: the smallest version that delivers the value proposition
- Explicitly out of scope for v1
- Constraints: platform, tech stack preferences, budget, timeline,
  integrations, hosting
- Success criteria: how we'll know the MVP works
- Open questions you need me to answer before planning can start

Ask me the open questions directly. Do not guess at answers.
Do not break this into tasks or phases. Do not write code.
>

Answer the open questions in your reply. The finished brief is what /cs-plan picks up from this session — skim it yourself before running Step 1, because nothing downstream re-derives it.

GGroundwork
Same session as Define
Normal · sonnet

Make the repo readable before you plan against it

Every later step opens AGENTS.md and the codebase. On an empty repo both are missing, so Review has nothing to review against and a fresh Build session starts from zero every time. Step G is Phase 0: it exists to make Step 1 possible.

It does not run the loop. The scaffold is mostly determined by the brief, and it is cheap to delete and regenerate, which by the gear rule above puts it well below the cost of a review cycle.

.claude/commands/cs-groundwork.md
---
description: Phase 0 scaffold and ground rules for a greenfield repo
---

This is a greenfield repo. Set up the ground rules before any feature work.

From the objective brief, write:

1. AGENTS.md, under 60 lines. One line on what this is, the stack, and the
   constraints that must never be violated. Leave the Commands section empty
   until the scaffold exists.
2. CLAUDE.md, containing @AGENTS.md plus any Claude Code specific lines.
3. docs/architecture.md: each decision from the brief with what was rejected
   and why. Not a stack list; package.json is the stack list.
4. docs/data-model.md: the schema, plus the ownership rules the schema does
   not express. Skip if there is no datastore.
5. PLAN.md from templates/PLAN.md, with this groundwork as Phase 0.

Do not invent conventions you have no basis for. If the brief does not
determine it, leave it out.

Then enforce in code what markdown cannot:
- .gitignore covering env files, build output, and local state
- .env.example, committed, keys only, no values
- lint, format, and typecheck installed and runnable
- one pre-commit or CI check that fails on a committed secret

Scaffold the project. Run every command you are about to put in AGENTS.md,
fix the ones that fail, and only then write them down.

Acceptance: I open a new session and ask what this project is and how to run
it. It answers from AGENTS.md alone, without reading source.
>

The last line is the whole test. If a fresh session can't orient itself from the files, Phase 0 isn't done, and every session after this one pays for it.

What not to write yet

AGENTS.md is for what the agent gets wrong without it. On day one you don't know what that is, and a long file of guessed conventions is worse than a short one, because the codebase will drift from it and you'll trust it anyway. Sixty lines is a ceiling, not a target.

Skills
A skill encodes a procedure you've run at least twice. Write them at a phase close, from what you actually did, not up front from what you imagine doing.
Path rules
.claude/rules/ scoped to paths that don't exist yet is dead weight. Add one the first time a constraint proves it needs enforcing in a specific directory.
File trees
A hand-maintained directory listing is stale within one session and derivable in one tool call. Write the rule instead: where things go, and why.
1Create Plan
Same session as Define
Exit plan mode to write · sonnet

Define the work

The objective becomes numbered tasks. Task IDs are what every later step points at instead of re-describing work in prose. Everything is written to disk here, not at Approval, so a lost session doesn't cost you the plan and so Review has something to open.

Two files, two jobs. PLAN.md is a short index that lists the phases and points at the current one. The phase file holds the tasks. There is no separate init step: the phase list is the plan's top level, so Step 1 creates it on the first run and corrects it on every run after.

layout
PLAN.md                       # index: phase list + current pointer
docs/plans/01-auth-shell.md   # done
docs/plans/02-offline-sync.md # current phase, task level detail
.claude/commands/cs-plan.md
---
description: Turn the objective brief into a phased plan on disk
argument-hint: [objective, or blank to use the brief from this session]
---

Create a complete implementation plan for the following objective:

$ARGUMENTS

If the line above is blank, work out what you are planning against, in this
order:

1. An objective brief produced earlier in this session: use it.
2. No brief, but PLAN.md exists: this is a phase boundary, and the objective
   is the phase `current:` names, or the first unticked phase if `current:`
   names a closed one. Read its line in PLAN.md, the closed phase file and
   its `.log.md` for what carries forward, AGENTS.md, and
   docs/architecture.md if it exists. Nothing else. The product scope is
   settled; do not re-derive it, and do not run /cs-define.
3. Neither: stop and tell me to run /cs-define first.

Coming in at a boundary you will have real questions — a one-line phase name
is an intention, not a specification. Ask them, per `## Also include` below,
before you write the file.

Break the work into logical phases, and phases into numbered tasks
(T1, T2, T3, ...).

## Files

PLAN.md is the index: a `current:` pointer and a checklist of phases in
dependency order, one line each, linking to their phase files. Create it from
templates/PLAN.md if absent; otherwise add or correct phases and set
`current:` to this one. Never copy task detail into PLAN.md.

Setting `current:` is yours alone. /cs-close leaves it on the phase it closed,
so at a boundary it still names the previous phase until you move it. Move it
in the same edit that writes the new phase file, never before.

Write the current phase to docs/plans/(NN)-(slug).md using
templates/phase.md. Detail only the current phase at task level. Phases
beyond it are provisional: reorder, split, merge, or drop them freely at each
boundary.

## Task graph

The phase file's frontmatter carries a machine-readable graph. One line per
task, exactly this shape, or the tooling cannot read it:

  T2: {deps: [T1], status: pending, files: [src/sync/queue.ts]}

- `deps` are task IDs in this phase only. Acyclic, and prefer depending
  backwards so IDs read in execution order.
- `files` is the complete set this task may open or write. A build session is
  bounded to this list plus its dependencies' files, so a missing entry stalls
  the build and an over-broad one wastes context. This is the single most
  important field you write.
- `status` starts as pending.

## Task body

One `## T(n)` section per task, matching the graph exactly:
- Goal
- Deliverables
- Acceptance Criteria
- Verify: the exact command I run and the exact output that means it passed.
  If the only check is visual, name the screen and what I should see. Never
  write "manually confirm it works".

## Size

Cap a phase at eight tasks. A ninth is a signal the phase should split: every
later session pays to read this file, so it stays small. Each phase must end
in a state I can run.

## Also include

- Assumptions you are proceeding on without confirming
- Open questions that need my input before this plan is final
- Out of scope items

Leave the `## Findings` and `## Changelog` sections in place and empty.
/cs-review writes the first, /cs-revise writes the second, and they are how those
sessions hand work to each other. Do not add a `reviewed:` field — the phase
has not been reviewed, and the tooling reads its absence.

Ask me the open questions directly rather than guessing. Do not write code.

## Finishing

1. `.claude/bin/plan lint` — fix anything it reports.
2. `.claude/bin/plan recommend` and print it. It will send you to /cs-review.
3. Stop, and tell me to run /cs-review in a NEW session. /cs-review typed here
   reviews its own work and will agree with itself.

The task graph

The phase file's frontmatter is machine-readable and its body is prose. Neither duplicates the other, and plan lint fails if they drift. One line per task, exactly this shape:

docs/plans/02-offline-sync.md
---
phase: 02-offline-sync
rev: 3
status: approved
workflow-rev: 1.3.0
tasks:
  T1: {deps: [], status: done, files: [src/db/schema.ts]}
  T2: {deps: [T1], status: pending, files: [src/sync/queue.ts, src/sync/types.ts]}
  T3: {deps: [T1], status: pending, files: [src/sync/worker.ts]}
  T4: {deps: [T2, T3], status: pending, files: [src/sync/index.ts]}
---

## T2 — write queue
Goal: ...
Acceptance Criteria: ...
Verify: `npm test -- queue` exits 0

files is the field that carries the most weight and the one most likely to be written carelessly. It is the contract a build session is bounded to: a missing entry stalls the build, an over-broad one spends context you don't get back. The linter can only check that it's non-empty, so Step 2 checks it against the actual codebase.

>

Eight tasks is the cap. Every session in the phase re-reads this file, so a ninth task isn't a longer plan — it's a phase that should have split.

Assumptions and open questions are kept separate on purpose: assumptions are commitments Review can challenge; open questions are things the model shouldn't be guessing at all.

>

The Verify line is load-bearing later. Build is not allowed to call a task done without running it and showing the output, so a task whose verification is "check that it works" is a task Build can pass by asserting. Write the command here or you lose the gate there.

>

Planning all fifty tasks up front produces fiction after roughly the tenth: T40 is written against a codebase state that won't survive T1 through T39. Task-level detail stops at the current phase boundary, and the phase list you write today is your least informed guess about phase four — it's meant to be rewritten.

2Review
New session — required
Plan mode · opus

Challenge the plan

Telling a model to "assume another team wrote it" does nothing if it's the same context that just wrote it: it still holds every assumption that produced the plan, and it cannot see what it never considered. Start a fresh session and hand it the file.

.claude/commands/cs-review.md
---
description: Independent review of the current phase, round 1
---

Run `.claude/bin/plan lint` and `.claude/bin/plan status` first. Treat every
E-code it prints as a Critical finding and every W-code as at least Medium,
then read PLAN.md, the phase file it points at, AGENTS.md, and the codebase.

You did not write this plan. Review it as an independent senior engineer
inheriting someone else's work. Be skeptical.

For each issue found, provide:
- Finding ID (F1, F2, ...)
- Severity: Critical, High, Medium, or Low
- Category: Missing work / Incorrect assumption / Risk / Task ordering /
  Architectural issue / Missing acceptance criteria / Unnecessary scope /
  Wrong file list
- Affected task ID(s)
- Description
- Recommended fix

Beyond the linter, which only checks shape:
- Treat any unresolved open question from the plan as Critical.
- Treat any task whose Verify line is not a runnable command or a named
  screen as High.
- Check every `files` list against the codebase. A task that will obviously
  need a file it does not list is High: it will stall a bounded build session.
- Check the dependency edges are true. The linter proves the graph is
  acyclic, not that T4 actually needs T2.
- Review the phase ordering in PLAN.md too, not just the tasks in this phase.

Order findings by impact. Do not inflate severity to look thorough — a Medium
labeled Critical is itself a review failure. If nothing rises above Medium,
say so and give the two things most likely to break anyway.

Do not rewrite the plan.
Critical High Medium Low
>

Zero findings on a fresh-session review of a whole phase means the reviewer didn't read the codebase. Check that it actually opened the files before you accept the result.

Round 2 and after: scope it

A second full review is a cold read of a plan that changed in three places, and it is the most expensive redundant thing in the loop. Once a changelog exists, re-review against the changelog rather than the whole phase — still in a new session, because independence is the point, not ignorance.

.claude/commands/cs-recheck.md
---
description: Scoped re-review against the changelog, round 2 and after
---

Run `.claude/bin/plan lint`. Then read the phase file's changelog and
frontmatter, and only the tasks the changelog names. Do not re-review the
phase end to end.

For each finding ID the changelog claims resolved, decide: actually resolved,
partially resolved, or not resolved. Quote the plan line that settles it.

Then check only three things beyond that:
- Did any resolution create a new dependency, ordering, or scope problem?
  New findings continue the existing numbering.
- Did any resolution change what a task touches without updating its `files`
  list?
- Did any Medium marked "not adopted" get a real reason, or a restatement of
  the finding?

End with one line: what this pass did NOT look at.
>

Stop condition: if round three still produces a Critical, the problem isn't the wording of the plan. The phase is too large or the objective is wrong. Split the phase and re-plan rather than revising a fourth time — a loop with no exit is how a planning workflow becomes a way of avoiding the build.

3Revise
Same session as Review
Exit plan mode to write · sonnet

Address the findings

Revise where the findings already live, so nothing has to be re-explained. Approval and any further review round both start a new session.

.claude/commands/cs-revise.md
---
description: Resolve findings in place and write the changelog
---

Revise the phase file in place. Bump `rev` in its frontmatter. Do not create a
second file. If a finding changes the phase ordering, update PLAN.md as well.

Resolve every Critical and High finding.
For each Medium finding, either implement the recommendation or state why it
was not adopted.
Low findings may be addressed at your discretion.

Preserve task IDs where possible. If tasks are added, removed, or split,
update the frontmatter graph in the same edit — the graph and the `## T(n)`
sections must stay in sync, and `.claude/bin/plan lint` will fail if they
drift. Run it when you are done.

Include a changelog mapping each finding ID to the resolution taken, and for
each one, the task ID or plan line that now carries the fix.

The finding-ID → resolution → plan-line changelog is what turns Approval into a checklist instead of a full re-read of the plan, and it's what the scoped round-2 review reads instead of the phase.

4Approval
New session — required
You sign it off
Normal · sonnet

Decide if it's ready

A model grading its own revision against criteria it just satisfied will pass itself every time. Two things follow from that, and rev 06 only did one of them. The model produces the evidence and you produce the verdict — and the evidence comes from a session that didn't write the revision. A fresh session reading the phase file and the changelog is cheap; it doesn't need the codebase.

.claude/commands/cs-approve.md
---
description: Readiness checklist with evidence, no verdict
---

Run `.claude/bin/plan lint`, then read the phase file and its changelog. You
did not write either. Do not approve or reject. Produce the readiness
checklist only.

For each line, give PASS or FAIL plus the evidence — quote the finding ID,
task ID, linter output, or plan line that proves it. "Looks fine" is a FAIL.

- The linter exits clean.
- Every Critical and High finding has a changelog entry, and the plan line it
  points at actually contains the fix.
- Every task has acceptance criteria and a Verify line I could run today.
- Every task's `files` list is complete enough that a session bounded to it
  could finish the task.
- Every remaining Medium/Low finding is explicitly accepted or justified.
- The phase ends in a state I can run.

Then list, in one line each, the riskiest thing still in the plan.

Do not set `status: approved`. I do that.

If the checklist is clean, set status: approved in the phase file's frontmatter yourself and open Build. That frontmatter line is the gate every later step reads; you are the only thing that writes it. If the checklist isn't clean, start a new session at Step 2 with the remaining finding IDs.

Flow

The loop

Not approved doesn't send you back to Define. The plan already exists as a file — you cycle Review → Revise → Approval until it clears, and each round that judges the previous one gets a clean session.

Dashed cyan is the retry loop, always in a new session. Orange is a build task that hit a wall: it writes the blocker into the phase file and re-enters at Review rather than redesigning on the spot. Mint is the exit once approved, and the per-task build loop. Groundwork is drawn dashed because it runs once, on an empty repo, and never again.

BBuild Mode
New session per task
Normal · sonnet · medium effort

Execute without redesigning

One task, one verification, one commit. State lives in the phase file and in git, not in the conversation, because a fresh session has no memory of the last one.

launch
claude --effort medium
.claude/commands/cs-build.md
---
description: Implement one approved task, verify it, commit, stop
argument-hint: [task-id]
---

Run `.claude/bin/plan brief $1`.

If $1 is blank, run `.claude/bin/plan next` and stop: tell me the runnable
task IDs and let me choose. If the brief prints BLOCKED, stop.

## Reading

Read exactly the files the brief lists, in the order it lists them, starting
with AGENTS.md. Nothing else. That order is fixed so the cached prefix is
reused across build sessions; do not read anything before it or reorder it.

If you need a file the brief does not list, stop and say which one and why.
That is a bug in the plan's `files` list, not something to work around.

If you need to locate something rather than read something, dispatch a search
subagent and take back the file:line answer only. Do not fill this session
with search output.

## Doing

Implement task $1 only. Do not change the architecture or the plan. Do not
start the next task. Restate the acceptance criteria and the Verify line
before you begin.

A task is done only when you have run its Verify command and shown me the
output. Not "the tests should pass" — the run, and what it printed. If there
is no runnable check, say so explicitly and tell me the single manual step I
have to take.

## Finishing

When the Verify output is clean:
1. `.claude/bin/plan done $1` — do not hand-edit the frontmatter.
2. Commit, with the task ID in the message.
3. Append to docs/plans/(NN)-(slug).log.md, ten lines maximum:
   `## $1` then only what the next session cannot work out from the repo —
   a decision you made that the plan did not specify, a gotcha you hit, a
   file whose actual contents differ from what the plan assumed. If there is
   nothing, write "nothing to carry". Never summarize the diff; git has it.
4. Run `.claude/bin/plan next` and print the result.
5. Stop. Exit the session rather than compacting.

If you hit a blocker:
- Stop. Do not work around it.
- `.claude/bin/plan block $1 "one line reason"`.
- Write it into the phase file as finding F(n) and tell me to re-enter at
  /cs-review.

The context envelope

plan brief T2 prints the read list: AGENTS.md, the phase file, then the files of every task T2 depends on transitively, then T2's own.

.claude/bin/plan brief T2
task    T2   status pending
phase   docs/plans/02-offline-sync.md  (phase status approved)
read    AGENTS.md
        docs/plans/02-offline-sync.md
        src/db/schema.ts
        src/sync/queue.ts
        src/sync/types.ts
        (nothing else; if you need a file that is not listed, stop and say so)
verify  `npm test -- queue` exits 0
handoff docs/plans/02-offline-sync.log.md  (read the last entry only)

Two things follow from reading exactly that list, in exactly that order. A wrong files entry surfaces as a session that stops and tells you, instead of one that quietly explores half the repo. And the prefix is identical across every build session in the phase, so everything before the task's own files is a cache read rather than a fresh one.

Searching is not reading. When a session needs to locate something it dispatches a subagent and takes back the file:line, so grep output never lands in the context that has to hold the task.

Handoffs on disk

Each task appends at most ten lines to docs/plans/NN-slug.log.md: decisions the plan didn't specify, gotchas, places the code differed from what the plan assumed. Never a summary of the diff — git has that. The next session reads the last entry, so nothing has to survive in a terminal you closed.

>

The Verify paragraph is the one addition that changes what this workflow produces. Without it, "acceptance criteria are met" is a judgement the model makes by reading its own diff, and a phase can close with every task marked done and nothing ever executed.

When two tasks can share a session

One session per task is the default, not a law. The reason for it is context hygiene — a session that already argued its way through T4 brings those assumptions to T5 — and that reason doesn't apply to two tasks that touch the same file with nothing structural between them. Rollback isn't the reason: git is the rollback, and it works the same either way.

Share a session
Consecutive tasks, same files, no schema, interface, or dependency change between them, and the first one's Verify passed. Commit separately per task ID anyway.
Always split
A task that crosses a module boundary, changes a shape another task depends on, or follows a task you had to correct. A corrected session is a polluted session.
Exit, don't compact
When the next-session prompt appears, exit the process. /compact reprocesses the whole conversation and then charges you to re-read the summary.

At the phase close

Corrections are the raw material for AGENTS.md, but you can't count them inside a session that only lives for one task. Collect them at the boundary instead, where you can see the whole phase.

.claude/commands/cs-close.md

description: Harvest repeated corrections, then close the phase
---

Run `.claude/bin/plan status`. If any task is not done, stop, say which, and
print `.claude/bin/plan recommend` — it names what to run instead.

Read this phase's commits, its log file, and the phase file including every
finding.

List the things I had to correct more than once across the phase, or that a
session got wrong because the repo never told it otherwise. Ignore one-off
mistakes.

For each, propose exactly one of:
- a line for AGENTS.md, if it applies everywhere
- a rule in .claude/rules/, if it only applies to one directory
- a skill, if it's a procedure we ran at least twice

Propose nothing you can't tie to a specific commit, log entry, or finding.

Then audit the delivered phase against its acceptance criteria and report
gaps, dead code, and anything left unwired.

Finally: tick this phase in PLAN.md, and set `status: closed` in the phase
file's frontmatter. Leave `current:` pointing at this phase. /cs-plan moves it
when it writes the next phase file, so the pointer never names a file that
does not exist yet.

## Next

- A next phase exists in PLAN.md: tell me to run `/cs-plan` for it in a NEW
  session. Name the phase and quote its PLAN.md line, so I can paste it if I
  want to. /cs-plan reads this closed phase and its log for what carries
  forward, and asks its open questions before it writes. Do not send me to
  /cs-define; the product scope was settled before Phase 01.
- No phase left: say the plan is complete, and do not invent one.

The new phase file starts unreviewed, so `plan recommend` picks the loop up
from /cs-review on its own once /cs-plan has written it.
>

PLAN.md is the one file nothing else updates on its own. If the phase-close instruction gets skipped, the index drifts and the next session confidently opens the wrong plan.

What /cs-close does not do is move current: to the next phase. That file does not exist until /cs-plan writes it, and a pointer at a file that isn't there is one no plan subcommand will read — leaving the boundary as the single place where the tool can't tell you what to run next. /cs-plan moves the pointer in the same edit that creates what it points at.

Nor does the boundary go back through /cs-define. /cs-define is the front door: it runs once, on a rough idea, and produces a product brief that lives in the session rather than on disk. By Phase 02 the product scope is settled and the useful context is on disk — the phase's line in PLAN.md, the phase you just closed, its log, AGENTS.md. /cs-plan opened cold reads exactly that, then asks what a one-line phase name can't say.

v1.0.0

What v1.0.0 added

The previous revision was a document you copied from. This one is a repo you install, and the three additions are the ones that only work with a tool underneath them.

Task graph
Dependencies, status, and a file list per task, in parseable frontmatter. plan lint catches cycles, forward references, tasks marked done ahead of their dependencies, missing Verify lines, and graph/body drift — so shape errors never burn a human review round.
Context envelope
Build reads the list plan brief prints and nothing else, in fixed order. A wrong file list now stops a session instead of quietly widening it, and the cached prefix is identical across every build session in the phase.
Dependency awareness
plan next picks the runnable task, --parallel groups the ones with no shared files, and plan done refuses a task whose dependency isn't finished. Rev 07 wrote dependencies down and nothing read them.
Handoffs on disk
The next-session note is appended to a log file instead of printed for you to paste. Ten lines, only what the repo can't tell you.
Phase cap
Eight tasks. Every session re-reads the phase file, so length is a recurring cost, not a one-off.
Search isolation
Locating something is a subagent returning file:line. Grep output stays out of the session that has to hold the task.
