Define → Plan → Review → Revise → Approve → Build

A six-step loop for planning software with an AI coding agent. Every step is gated by task IDs and finding IDs, so nothing moves forward on a vague "looks good." State lives on disk from Step 1 in PLAN.md and a phase file, and every step that judges the previous one runs in a fresh session so it can't inherit the assumptions it's supposed to catch.

SScale

Pick a gear first

The full loop costs four sessions before a line of code exists. That pays for itself on a new surface area and is pure overhead on a copy change. Match the gear to the blast radius, not to the enthusiasm.

Direct
Skip the workflow. Reversible, one or two files, obvious correct answer. Just ask for the change.
Short loop
Plan → Review → Build, one session, no files on disk. A feature inside existing architecture. Skip Define, Revise inline, no formal approval.
Greenfield
Define → Groundwork → full loop. Empty repo. Nothing to read, no conventions to follow, no commands that work. Step G exists to end that state before Step 1 runs.
Full loop
All six steps, split across sessions. New app, new phase, schema changes, auth, payments, anything where being wrong is expensive to unwind.
>

Touching data ownership, auth, or money puts you in the full loop regardless of how small the diff looks.

RRuntime

Route the model to the step

This section describes Claude Code's optional model routing. Codex runs the same workflow with the model, effort, and collaboration mode selected for the active Codex session.

Planning is worth the expensive model. Executing an approved spec is not. Rather than remembering that at 4am, let the alias do it: in opusplan, plan mode runs Opus and execution runs Sonnet.

.claude/settings.json
{
  "model": "opusplan",
  "env": {
    "CLAUDE_CODE_SUBAGENT_MODEL": "sonnet"
  }
}

Which gives one rule for the whole workflow: reason in plan mode, exit plan mode to write. The thinking runs on Opus, the typing runs on Sonnet, and the reasoning is already in context by the time the cheaper model does the writing.

>

Exiting plan mode changes model, and the next response re-reads the full history without cached context. That's fine once per session and expensive if you toggle back and forth. Reason, exit, write, stop.

Build effort
Launch build sessions with claude --effort medium. The ladder is low / medium / high / xhigh / max, the default is high, and a task that already survived a review cycle doesn't need it.
Check the defaults
A model chosen with /model is saved into ~/.claude/settings.json and quietly applies to every session after. effortLevel in the same file behaves the same way. Clear both keys so the project setting and the launch flag win.
Never switch mid-session
Set the model at launch with --model, which is session-only. Switching inside a long conversation re-reads the entire history uncached.

Every step below carries the mode and model it should run on.

CCommands

Commit the prompts, don't paste them

The prompts below are long on purpose, and pasting a 30-line block by hand at every step is where this workflow rots. The text drifts between projects, an improvement you make today is invisible to every repo already mid-phase, and nothing records which version of the loop a given plan was built under.

Commit each step as a command file instead. The page you're reading then holds the reasoning — why a fresh session, why the gear rule — and the repo holds the executable version, which git can diff.

How a command file works

A command is a markdown file in .claude/commands/. The filename becomes the slash name, so cs-build.md gives you /cs-build. The frontmatter is metadata for the picker; the body below it is the prompt, sent verbatim. $ARGUMENTS is replaced by everything you typed after the command name, and $1 by the first word of it. Put the files in .claude/commands/ to commit them with the repo, or ~/.claude/commands/ to have them everywhere.

Codex uses repository-scoped skills instead. The installer adds eleven canonical adapters plus an explicit-only compatibility alias under .agents/skills/; each one loads a runtime-patched copy of the same canonical command from .agents/coldsession/commands/. Invoke /cs-build T2 in Claude Code or $cs-build T2 in Codex. The product-specific sigil differs; the cs-* stem and arguments are the same.

every prompt below is one of these
.claude/commands/
├── cs-define.md      /cs-define <rough idea>   step 0
├── cs-groundwork.md  /cs-groundwork            step G, greenfield only
├── cs-plan.md        /cs-plan                  step 1
├── cs-review.md      /cs-review                step 2, every round
├── cs-recheck.md     /cs-recheck               deprecated 2.x alias
├── cs-revise.md      /cs-revise                step 3
├── cs-approve.md     /cs-approve               step 4
├── cs-build.md       /cs-build T7              build, one task
├── cs-close.md       /cs-close                 phase close
└── cs-status.md      /cs-status                where am I

.claude/bin/plan   the task graph tool every command above calls

Each step below shows the load-bearing part of its command contract. The installed files in commands/ are canonical; the excerpts explain state and context boundaries without duplicating every line.

What a command does not carry

This is the part that bites. A command supplies the prompt text and nothing else. It does not start a new session, enter plan mode, or pick a model. A review in the session that wrote the plan inherits its assumptions. The installed Claude hook can refuse that command; on the Codex surface, keeping the review cold remains an instruction the session must follow.

You do
Start the session, enter or exit plan mode, set --effort at launch. The session and mode chips on each step below are still the instruction — a command file cannot start a session or pick a model for you. A hook can refuse a judging command in the wrong one; see below.
Settings do
Model routing, via opusplan in .claude/settings.json. Plan mode gets Opus, execution gets Sonnet, with no per-command configuration.
The command does
The prompt text, the argument substitution, and the fact that it's the same text in every repo and every run.

Where the prompt stops and a program starts

Everything above is advisory. A command asks a model to do something, and the model usually does it — but "usually" is the whole problem for the rules this workflow rests on. Four of them are decidable by a program, at no model cost, so on Claude Code a program decides them. They install to .claude/hooks/ and register in .claude/settings.json.

Cold session
UserPromptSubmit refuses /cs-review, /cs-approve, or /cs-close after /cs-plan or /cs-revise in the same session (E25). The /cs-recheck alias receives the same check.
Bounded reads
PreToolUse checks Read, Edit, and Write while a task is in_progress. Repository paths outside the allowed context are refused (E23).
Human approval
PreToolUse refuses an Edit or Write that introduces status: approved into a phase file (E24). Preserving an existing approved status is allowed.
Lint on write
PostToolUse reports E-codes after a phase file is edited or written, including a new phase before current: points at it. It reports errors after the write; it does not undo it.

Each hook ships as an .sh/.cmd wrapper pair that passes the event to plan guard. Both installers quote hook paths so projects with spaces in their directory names work. Decisions live in the same Python runtime that computes plan brief.

The path gate allows the union of all in-progress tasks' briefs, plus PLAN.md, the phase file, and its handoff log. It cannot identify which parallel session owns a task. Paths outside the repository and shell commands are outside this path check; each Build session must still follow its own brief.

guard fails open when the state needed for a check is absent, unreadable, or ambiguous. The cold-session gate requires both session history and a readable current phase; the path gate requires an in-progress task. Lint-on-write checks the written phase itself, even before PLAN.md exists. Allowed or unrecognised invocations exit 0 silently; positive violations report their codes on stderr and exit 2. A bare plan guard is silent too; its usage lives in plan --help.

>

Codex has no hook mechanism, so there all four rules stay prompt text. The surfaces are identical in commands, phase format, and tooling, and differ in enforcement — worth knowing before you assume a rule holds because it held yesterday on the other one.

Turn the idea into an objective

Run this once, before Step 1 has anything to plan. It converts a rough idea into a scoped, planning-ready file that survives a cold session.

.claude/commands/cs-define.md
Entry guard:
- PLAN.md exists: stop without opening OBJECTIVE.md.
- OBJECTIVE.md exists: stop unless --revise was explicit.
- An interrupted revision continues only with --revise --resume.

Ask every blocking scope, user, constraint, and success question, in rounds:
one round is every question whose prerequisites are settled, asked together and
numbered, each with a recommended answer. Find facts with a search subagent
rather than asking. Stop when nothing is left open. Then write
OBJECTIVE.md once from templates/OBJECTIVE.md with objective-rev, status:
ready, one smallest end-to-end journey, measurable success criteria, explicit
exclusions and assumptions, and `Open questions: None.`

Do not write tasks, phases, placeholders, TODOs, or unanswered alternatives.

The questions arrive in rounds, not one at a time. A round is every decision whose prerequisites are already settled, asked together and numbered, each with the answer the session recommends — so you can accept a whole round in a line instead of writing prose five times over. Your answers settle those decisions and unblock the ones that depended on them, and that is the next round. Anything the session could look up is never a question: it dispatches a search subagent and keeps only the answer. The interview ends when nothing is left open, and that emptiness is exactly what triggers the single write of OBJECTIVE.md.

>

Answer the open questions, inspect OBJECTIVE.md, then end the session. Groundwork or the first Plan reads that file cold; no conversational handoff is required.

Normal · sonnet

Make the repo readable before you plan against it

Every later step opens AGENTS.md and the codebase. On an empty repo both are missing, so Review has nothing to review against and a fresh Build session starts from zero every time. Step G is Phase 0: it exists to make Step 1 possible.

It does not run the loop. The scaffold is mostly determined by the brief, and it is cheap to delete and regenerate, which by the gear rule above puts it well below the cost of a review cycle.

.claude/commands/cs-groundwork.md
Require ready OBJECTIVE.md and no PLAN.md. Claim `active: groundwork`; a
duplicate stops and an interrupted run requires --resume.

Create the verified scaffold, concise AGENTS.md, architecture decisions,
optional data model, runnable quality commands, and secret check. Only after
they pass, write a valid closed Phase 00 and create PLAN.md last with Phase 00
checked plus provisional product phases. Remove the active marker.

PLAN.md is the completion boundary. The next Plan will not read OBJECTIVE.md.
>

The last line is the whole test. If a fresh session can't orient itself from the files, Phase 0 isn't done, and every session after this one pays for it.

What not to write yet

AGENTS.md is for what the agent gets wrong without it. On day one you don't know what that is, and a long file of guessed conventions is worse than a short one, because the codebase will drift from it and you'll trust it anyway. Sixty lines is a ceiling, not a target.

Skills
A skill encodes a procedure you've run at least twice. Write them at a phase close, from what you actually did, not up front from what you imagine doing.
Path rules
.claude/rules/ scoped to paths that don't exist yet is dead weight. Add one the first time a constraint proves it needs enforcing in a specific directory.
File trees
A hand-maintained directory listing is stale within one session and derivable in one tool call. Write the rule instead: where things go, and why.

New session
Exit plan mode to write · sonnet

Define the work

The objective becomes numbered tasks. Task IDs are what every later step points at instead of re-describing work in prose. Everything is written to disk here, not at Approval, so a lost session doesn't cost you the plan and so Review has something to open.

Two files, two jobs. PLAN.md is a short index that lists the phases and points at the current one. The phase file holds the tasks. There is no separate init step: the phase list is the plan's top level, so Step 1 creates it on the first run and corrects it on every run after.

layout
PLAN.md                       # index: phase list + current pointer
docs/plans/01-auth-shell.md   # done
docs/plans/02-offline-sync.md # current phase, task level detail
.claude/commands/cs-plan.md
Check whether PLAN.md exists before opening OBJECTIVE.md.

No PLAN.md: require ready OBJECTIVE.md and read it once. Copy objective-rev
into PLAN.md. Arguments may clarify but cannot silently override the file.

PLAN.md exists: never open or search OBJECTIVE.md. Plan only after a closed
boundary, from its index line, closed phase, last log entry, AGENTS.md,
architecture notes, and targeted repository inspection. An interrupted Plan
requires --resume; an active phase is never rewritten.

Write one phase of at most eight tasks. Each task has true dependencies, a
complete minimal files list, observable acceptance criteria, and an exact
Verify command. Size each task at the lowest rung that holds: no task at all,
a configuration change, an extension, a new file, a new abstraction.

Apply the project's own policy-* skills: read each description, open only the
ones this phase can violate, record what you considered under ## Policy.

Resolve blocking questions first, as one round of numbered questions carrying
recommended answers; two rounds at the outside. Record `Open questions: None.`
Move current: only after the new phase exists and lints.

Plan asks in the same rounds Define does, but capped: one, or two at the outside. Phase scope is not product scope, and a phase that needs a third round of questions is telling you it is really two phases. That is the same signal the linter raises as W05 when a third review round still turns up a Critical.

The rung ladder is where over-building gets caught while it is still free to fix. Ask what the smallest change satisfying the goal is and stop at the first rung that holds: often no task at all, because something already does it; failing that a flag, an extension of code that exists, a new file, and only then a new abstraction. This is not tidiness. A task sized one rung high widens its files list, and files is the envelope every Build session is bounded to — so the cost is paid again on every read of that task, by sessions that never saw the decision.

Policy the project owns

Brand, security, privacy, compliance, UX. Every organisation has rules a plan can break without breaking a test, and none of them belong to a planning workflow — they belong to the project. The enterprise shape for this is a spec.md stage between intent and plan, reviewed by whoever owns the policy. That is a fifth session, and this loop already costs four before a line of code exists.

So policy lands as skills the project writes and owns, named policy-*, in the skills directory the agent already reads: .claude/skills/ under Claude Code, .agents/skills/ under Codex. The cs-* skills are this workflow's own invocation adapters and carry no policy; the prefix is what keeps them apart, and it is why an install or uninstall, which only touches cs-*, can never disturb the project's own.

docs/plans/02-offline-sync.md
## Policy

policy-a11y | T2, T4 | contrast and focus order on the new list view
policy-billing | - | not applicable; this phase touches no pricing surface

Plan lists them, reads only each skill's frontmatter description, and opens in full just the ones this phase could actually violate. An applicable one constrains the phase like any durable constraint: it can add acceptance criteria, add a task, or put a file in files that the goal alone would not have needed — and that is the point of doing it here rather than at Build, where the read envelope is already closed.

Step 2 lists the same skills itself instead of trusting the section above, since that section is the judgement it is checking, and files each miss as a Policy finding. From there nothing is new: an open Critical or High blocks approval whatever its category, Approve demands a changelog line that names what settled it, and plan metrics counts it with the rest. A policy violation inherits the whole machine because it is just a finding.

>

A project with no policy-* skill has no policy layer. Plan writes None., Review files nothing, and the absence is never itself a finding — the same fail-open instinct the hooks have.

Policy skills can exist before a procedure has run twice. The repetition rule at phase close applies to procedures learned from corrections; an established policy must inform the first plan that could violate it.

The task graph

The phase file's frontmatter is machine-readable and its body is prose. Neither duplicates the other, and plan lint fails if they drift. One line per task, exactly this shape:

docs/plans/02-offline-sync.md
---
phase: 02-offline-sync
rev: 3
status: approved
reviewed: 3
ready: 3
workflow-rev: 1.4.0
tasks:
  T1: {deps: [], status: done, files: [src/db/schema.ts]}
  T2: {deps: [T1], status: pending, files: [src/sync/queue.ts, src/sync/types.ts]}
  T3: {deps: [T1], status: pending, files: [src/sync/worker.ts]}
  T4: {deps: [T2, T3], status: pending, files: [src/sync/index.ts]}
---

## T2 — write queue
Goal: ...
Acceptance Criteria: ...
Verify: `npm test -- queue` exits 0

files is the field that carries the most weight and the one most likely to be written carelessly. It is the contract a build session is bounded to: a missing entry stalls the build, an over-broad one spends context you don't get back. The linter can only check that it's non-empty, so Step 2 checks it against the actual codebase.

>

Eight tasks is the cap. Every session in the phase re-reads this file, so a ninth task isn't a longer plan — it's a phase that should have split.

Assumptions and open questions are kept separate on purpose: assumptions are commitments Review can challenge; open questions are things the model shouldn't be guessing at all.

>

The Verify line is load-bearing later. Build is not allowed to call a task done without running it and showing the output, so a task whose verification is "check that it works" is a task Build can pass by asserting. Write the command here or you lose the gate there.

>

Planning all fifty tasks up front produces fiction after roughly the tenth: T40 is written against a codebase state that won't survive T1 through T39. Task-level detail stops at the current phase boundary, and the phase list you write today is your least informed guess about phase four — it's meant to be rewritten.

2Review
New session — required
Plan mode · opus

Challenge the plan

Telling a model to "assume another team wrote it" does nothing if it's the same context that just wrote it: it still holds every assumption that produced the plan, and it cannot see what it never considered. Start a fresh session and hand it the file.

.claude/commands/cs-review.md
Run `plan begin review [--resume]` before any other read. A duplicate stops;
only the matching interrupted pass may resume.

With no reviewed: field, inspect the full plan and codebase independently.
When reviewed is lower than rev, inspect only the current changelog entries
and affected tasks. Record each issue once in the seven-field Findings shape.
For an over-built task, name the rung it should have stopped at and make that
rung the fix: Medium normally, High when it widens files past the goal.
List the project's policy-* skills yourself rather than trusting the phase's
## Policy section, and file each miss under the category Policy.

Run `plan finish review` to set reviewed: and clear the marker atomically,
then lint and print `plan recommend`. A completed revision review names what
its intentionally narrow scope did not inspect.
Critical High Medium Low
>

Zero findings on a fresh-session review of a whole phase means the reviewer didn't read the codebase. Check that it actually opened the files before you accept the result.

Categories are free text and the linter does not check them, but three are named so a later pass can count like with like: Task ordering, Unnecessary scope, and Policy. Severity never follows the category — a privacy policy breach is Critical, a copy deviation is Medium.

Round 2 and after: the same command narrows its scope

A second full review is a cold read of a plan that changed in three places, and it is the most expensive redundant thing in the loop. Once a changelog exists, /cs-review compares reviewed: with rev: and checks the changelog and affected tasks rather than the whole phase — still in a new session, because independence is the point, not ignorance.

/cs-recheck remains installed only as a deprecated 2.x compatibility alias. It delegates to /cs-review and is never emitted by plan recommend.

>

Stop condition: if round three still produces a Critical, the problem isn't the wording of the plan. The phase is too large or the objective is wrong. Split the phase and re-plan rather than revising a fourth time — a loop with no exit is how a planning workflow becomes a way of avoiding the build.

3Revise
Same session as Review
Exit plan mode to write · sonnet

Address the findings

Revise where the findings already live, so nothing has to be re-explained. Approval and any further review round both start a new session.

.claude/commands/cs-revise.md
Run `plan begin revise [--resume]`, then `plan bump`. The bump occurs exactly
once and becomes a no-op when an interrupted pass resumes.

Resolve Critical and High findings, resolve or justify Medium findings, and
keep task bodies and graph entries synchronized. Close each finding with
`plan resolve`, naming the task or plan line carrying the result.

After lint, `plan finish revise` clears the marker. `plan recommend` sends the
new revision to Review before any remaining open finding can trigger Revise.

The finding-ID → resolution → plan-line changelog is what turns Approval into a checklist instead of a full re-read of the plan, and it's what the scoped round-2 review reads instead of the phase.

New session — required
You sign it off
Normal · sonnet

Decide if it's ready

A model grading its own revision against criteria it just satisfied will pass itself every time. Two things follow from that, and rev 06 only did one of them. The model produces the evidence and you produce the verdict — and the evidence comes from a session that didn't write the revision. A fresh session reading the phase file and the changelog is cheap; it doesn't need the codebase.

.claude/commands/cs-approve.md
Run `plan begin approve [--resume]` before reading the phase. Produce an
evidence-backed PASS/FAIL checklist and one highest-residual-risk line:

  Risk — impact — mitigation with task/line evidence — exact remaining action

Every actionable FAIL or unmitigated risk becomes a deduplicated open finding
with a concrete plan edit, then `plan finish approve --fail` routes to Revise.
A clean `plan finish approve --pass` writes ready: <rev> and clears the marker.
It never sets status: approved; the human still does that.

If the checklist is clean, the matching ready: marker prevents an accidental second Approve while it waits for you to set status: approved. If it is not clean, Revise reads the persisted findings and the following Review runs cold.

Flow

The loop

Not approved doesn't send you back to Define. The plan already exists as a file — you cycle Review → Revise → Approval until it clears, and each round that judges the previous one gets a clean session.

Dashed cyan is the retry loop, always in a new session. Orange is a build task that hit a wall: it writes the blocker into the phase file and re-enters at Review rather than redesigning on the spot. Mint is the exit once approved, and the per-task build loop. Groundwork is drawn dashed because it runs once, on an empty repo, and never again.

BBuild Mode
New session per task
Normal · sonnet · medium effort

Execute without redesigning

One task, one verification, one commit. State lives in the phase file and in git, not in the conversation, because a fresh session has no memory of the last one.

launch
claude --effort medium
.claude/commands/cs-build.md
---
description: Implement one approved task, verify it, commit, stop
argument-hint: [task-id] [--resume]
---

Run `plan start T(n) [--resume]` before reading files. It refuses an
unapproved, done, blocked, or dependency-blocked task. A task already
in_progress requires explicit --resume. Then run `plan brief T(n)`.

## Reading

The brief's `read` block gives the file order, starting with AGENTS.md. Use
inlined context and follow the phase/handoff annotations. That order is fixed
so the cached prefix is reused across build sessions; do not read anything
before it or reorder it.

If you need a file the brief does not list, stop and say which one and why.
That is a bug in the plan's `files` list, not something to work around.

If you need to locate something rather than read something, dispatch a search
subagent and take back the file:line answer only. Do not fill this session
with search output.

## Doing

Implement that task only. Do not change the architecture or the plan. Do not
start the next task. Restate the acceptance criteria and the Verify line
before you begin.

The acceptance criteria is a ceiling, not a floor. Take the lowest rung that
satisfies it, and prefer a native or already-present primitive over a new
component. Add no error handling, configuration, or abstraction it did not ask
for. If the task was specified a rung too high, build the lower one that meets
the criteria and note the mismatch in the phase log.

A task is done only when you have run its Verify command and shown me the
output. Not "the tests should pass" — the run, and what it printed. If there
is no runnable check, say so explicitly and tell me the single manual step I
have to take.

## Finishing

When the Verify output is clean:
1. Append to docs/plans/(NN)-(slug).log.md, ten lines maximum:
   `## T(n)` then only what the next session cannot work out from the repo —
   a decision you made that the plan did not specify, a gotcha you hit, a
   file whose actual contents differ from what the plan assumed. If there is
   nothing, write "nothing to carry". Never summarize the diff; git has it.
2. `.claude/bin/plan done T(n)` — only in_progress tasks can finish.
3. Commit task changes, phase state, and log together with the task ID.
4. Run `.claude/bin/plan recommend` and stop.

If you hit a blocker:
- Stop. Do not work around it.
- `.claude/bin/plan block T(n) "one line reason"`.
- Write it into the phase file as finding F(n) and tell me to re-enter at
  /cs-review.

The context envelope

plan brief T2 prints the read list: AGENTS.md, the phase file, then the files of every task T2 depends on transitively, then T2's own.

.claude/bin/plan brief T2
task    T2   status in_progress
phase   docs/plans/02-offline-sync.md  (phase status approved)
read    AGENTS.md
        docs/plans/02-offline-sync.md  (own section inlined below; open only for Assumptions, Policy, or another task)
        src/db/schema.ts
        src/sync/queue.ts
        src/sync/types.ts
        (nothing else; if you need a file that is not listed, stop and say so)
section T2
        Goal: ...
        Acceptance Criteria: ...
        Verify: `npm test -- queue` exits 0
budget  ~3,400 tokens across 4 file(s): ~900 phase file, ~2,500 task-owned
verify  `npm test -- queue` exits 0
handoff docs/plans/02-offline-sync.log.md  (last entry inlined below; open the file only for more)
        ## T1 handoff

        Schema migration landed; queue table has a `sent_at` column T2 can
        check before retrying.

Two things follow from reading exactly that list, in exactly that order. A wrong files entry surfaces as a session that stops and tells you, instead of one that quietly explores half the repo. And the prefix is identical across every build session in the phase, so everything before the task's own files is a cache read rather than a fresh one.

On Claude Code this list is enforced, not requested: while the task is in_progress, a read outside it is refused with the task id. That is the largest token lever in the workflow, and not because it deletes prompt lines — it deletes the session that would otherwise have read a codebase instead of four files.

Searching is not reading. When a session needs to locate something it dispatches a subagent and takes back the file:line, so grep output never lands in the context that has to hold the task.

Handoffs on disk

Each task appends at most ten lines to docs/plans/NN-slug.log.md: decisions the plan didn't specify, gotchas, places the code differed from what the plan assumed. Never a summary of the diff — git has that. The next session reads the last entry, so nothing has to survive in a terminal you closed.

>

The Verify paragraph is the one addition that changes what this workflow produces. Without it, "acceptance criteria are met" is a judgement the model makes by reading its own diff, and a phase can close with every task marked done and nothing ever executed.

When two tasks can share a session

One session per task is the default, not a law. The reason for it is context hygiene — a session that already argued its way through T4 brings those assumptions to T5 — and that reason doesn't apply to two tasks that touch the same file with nothing structural between them. Rollback isn't the reason: git is the rollback, and it works the same either way.

Share a session
Consecutive tasks, same files, no schema, interface, or dependency change between them, and the first one's Verify passed. Commit separately per task ID anyway.
Always split
A task that crosses a module boundary, changes a shape another task depends on, or follows a task you had to correct. A corrected session is a polluted session.
Exit, don't compact
When the next-session prompt appears, exit the process. /compact reprocesses the whole conversation and then charges you to re-read the summary.

Who opens the next session

The rule that a judging step runs cold has always been enforced by making you do it: quit the session, start another, retype the command. Three to five times a phase. That is friction sitting directly on the workflow's load-bearing claim, and friction there is not neutral — it is the thing that gets skipped on the day you are in a hurry, and a review that never happened is at least honest about it. The failure mode worth fearing is the other one: running the review in the session that wrote the plan, getting the right wording without the independence, and believing it.

An editor that can open a second terminal removes the tax without touching the rule. /cs-cold starts a separate process with its own session id and empty scrollback and hands it the command. The important part is what it does not do: it is not a flag on /cs-review, because the gate matches the command name in the prompt and a flag would need an exception carved into the one function the guarantee rests on. A separate command is not a judging command, so the gate is untouched and the new session's own guard clears the step on its own merits. The automation goes through the gate, not around it.

Supervision is deliberately absent. A coordinator watching the cold session would give it a reason to report back, and not reporting back is what makes it independent. It is a handoff and then silence.

How wide parallel builds go

plan next --parallel partitions runnable tasks by file overlap, so a group is disjoint by construction and safe to build at once. The usual advice — two sessions, no more — was never about the tasks. It was about a human watching terminals, and it stops applying the moment something else is doing the watching.

Two things had to be true first. Every phase-file mutation is a read-modify-write of the whole file, so overlapping commands silently dropped one of the two writes; that was already a latent race for anyone running two terminals by hand, and a certainty at six. And the read gate allowed the union of every in-progress task's read set, because a hook could not tell which session owned which task — so the bounded read list, the largest token lever in the workflow, loosened with every session added. The write race is closed everywhere: plan start stamps the claiming session — Orca's terminal handle covers a Codex worker inside Orca as well as a Claude one — and every mutating command takes a lock regardless of surface. The read gate is a different story: only Claude enforces it, because only Claude has the hook that calls it. A stamped Codex worker still gets no narrower reads than the union; it stays inside the brief because /cs-fanout tells it to, not because anything refuses a wider read.

At the phase close

Corrections are the raw material for AGENTS.md, but you can't count them inside a session that only lives for one task. Collect them at the boundary instead, where you can see the whole phase — and only write one down on its second occurrence. The first time is signal, not yet a pattern, even when it was caused by missing repository guidance. Once AGENTS.md hits its sixty-line budget (plan lint warns W06 past that, never blocking a build), the close audit names the line a new one replaces instead of appending — the file's growth stays bounded by the rule that fills it, not by a linter noticing afterward.

.claude/commands/cs-close.md
Run `plan begin close [--resume]`; only an approved phase with every task done
can claim Close. Audit commits, logs, findings, and acceptance criteria.

A material gap becomes an open finding and `plan finish close --fail` demotes
the phase to draft for Revise. On a clean audit, `plan finish close --pass`
ticks the PLAN.md line, marks the phase closed, clears the marker, and leaves
current: on that file. The next Plan reads this handoff, never OBJECTIVE.md.
>

PLAN.md is the one file nothing else updates on its own. If the phase-close instruction gets skipped, the index drifts and the next session confidently opens the wrong plan.

What /cs-close does not do is move current: to the next phase. That file does not exist until /cs-plan writes it, and a pointer at a file that isn't there is one no plan subcommand will read — leaving the boundary as the single place where the tool can't tell you what to run next. /cs-plan moves the pointer in the same edit that creates what it points at.

Nor does the boundary go back through /cs-define. /cs-define is the front door: it runs once and persists the product brief in OBJECTIVE.md. The first Plan consumes it; once PLAN.md exists the objective is never read again. By Phase 02 the useful bounded context is the phase's line in PLAN.md, the phase you just closed, its log, AGENTS.md. /cs-plan opened cold reads exactly that, then asks what a one-line phase name can't say.

Workflow health

Use the phase history to improve the next plan

At a phase boundary, run plan metrics to inspect every readable phase under docs/plans/. It works independently of PLAN.md and its current pointer, using recorded state and git history without a model call.

installed runtime · choose your surface
# Claude Code installation
.claude/bin/plan metrics
# Codex installation
.agents/coldsession/bin/plan metrics
# PowerShell: use plan.cmd in the same directory.
Leading indicators
Revisions to approval, first-pass approval rate, currently blocked tasks, and review rounds. Use them to spot phases that need smaller scope or more complete task file lists.
Lagging indicators
Findings by severity, reopen entries in closed phases, resolved versus accepted findings, and phase cycle time from git history. Use these alongside the close audit to choose the next process correction.

These are summaries of recorded state: review rounds use rev:, and blocked tasks reflect current status rather than every past blockage. Missing approval or git history is reported as n/a. With no phase files, metrics prints a message and exits 0. Unlike the hook-invoked guard, it has a human reader and reports an empty result explicitly.

v2.5.0

What v2.5.0 adds

This release makes the token cost of a build session visible rather than assumed, and then spends that visibility on the largest single item in it: the whole phase file, which every task's brief has always included in full. plan brief now reports the approximate size of the context it just bounded and inlines the task's own section instead of pointing at the file for it, plan lint flags a task whose own files (not the phase file) have grown past budget, and plan metrics tracks the average across phase history. All of it is advisory, computed from what a phase file already declares, and adds nothing to the phase format -- plan guard's read gate is unchanged, so nothing a task could read before is newly refused after upgrading.

The phase file, scoped
plan brief inlines the task's own ## T(n) section -- Goal, Deliverables, Acceptance Criteria, Verify -- so a build session gets it without opening the phase file, which otherwise carries every other task's section too and can outweigh the task's actual files many times over. The file stays in the read list for Assumptions, Policy, or another task's detail; the budget line reports its share separately so a long phase file no longer makes every task in it look over-scoped. The handoff log's last entry is inlined the same way, rather than pointed at and trusted to stop a session short of the whole log.
Context budget
plan brief prints an approximate token count for the bounded read list it just resolved, broken into the phase file's share and the task's own. plan lint's new W07 flags a task whose own files (plus its dependencies') cross a 12,000-token soft budget, the same way W06 already flags an oversized AGENTS.md. Advisory only: it never changes an exit code, so a project that updates coldsession sees new output, never a new failure.
Cold sessions, spawned
/cs-cold starts the next step in a new Orca session and stops. Not a flag on the judging commands: a separate command passes through the gate instead of needing an exception inside it.
Supervised fanout
/cs-fanout builds one disjoint group as Orca workers, relays their questions, and reports outcomes. The coordinator never builds a task or marks one done.
Owned claims
plan start stamps the calling session onto the task, Orca's terminal handle first: a Codex worker inside Orca gets one exactly as a Claude one does. The read gate then scopes to the owning task instead of the union — but that gate is a Claude hook, so only Claude enforces it; a Codex worker still relies on its dispatch brief. An unstamped claim (a 1.4 phase file, or any session with no id -- a Codex session outside Orca) falls back to the union, as before.
Locked writes
Mutating commands take an exclusive lock on the phase file for their whole span, because the stale read happens long before the write. Read-only commands take none, and guard above all.
Board mirroring
Inside Orca, phase state follows onto the workspace card at each transition. Gated on the worktree environment, best-effort, and silent: outside Orca no subprocess runs at all.
Deterministic gates
Four Claude hook pairs call plan guard for cold judging sessions, bounded file access, human approval, and lint-on-write. The shipped Codex adapters retain advisory instructions.
Project policy
Plan applies relevant host-owned policy-* skills and records its judgement in ## Policy. Review independently checks coverage. Installers leave the project's policy skills alone.
Bounded guidance
W06 warns when AGENTS.md exceeds 60 lines. Close proposes guidance on a correction's second occurrence and names a replacement line when the budget is full.
Workflow metrics
plan metrics reports leading and lagging indicators across the phase history, even without a current phase pointer.
Prompt evals
Three manual Claude fixtures grade command behavior from machine-readable state and tool traces. Standard unit tests cover the grading logic without live model calls.
Release fixes
Quoted hook paths, matching installer filters, alias-aware session checks, and linting before the pointer moves. Version checks keep install pins aligned with the tool.
